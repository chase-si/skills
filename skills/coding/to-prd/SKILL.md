This skill takes the current conversation context and codebase understanding and produces a PRD. Do NOT interview the user — just synthesize what you already know.

The issue tracker and triage label vocabulary should have been provided to you — run `/setup-matt-pocock-skills` if not.

## Process

1. Explore the repo to understand the current state of the codebase, if you haven't already. Use the project's domain glossary vocabulary throughout the PRD, and respect any ADRs in the area you're touching.

2. Sketch out the major modules you will need to build or modify to complete
the implementation. Actively look for opportunities to extract deep modules
with small, stable public interfaces.

A deep module (as opposed to a shallow module) encapsulates substantial
functionality behind a simple interface that rarely changes.

3. Identify the public test seams that prove the feature's observable
behaviour. Prefer existing seams to new ones and the highest practical seam
that can prove an acceptance criterion without reaching into implementation
details. Use multiple seams only when distinct boundaries or risks require
them; do not create an interface solely to make a shallow test convenient.

Map every user story to externally observable acceptance criteria and the seam
through which each criterion will be verified. Record whether verification is
automated or human and why.

Check with the user that the module boundaries, critical behaviours, and test
seams match their expectations. Ask which risks require the strongest proof;
do not ask them to choose internal modules merely for test coverage.

4. If the project issue tracker is GitHub, ensure the PRD workflow labels exist before publishing. First check existing labels with `gh label list`. If either label is missing, create it with the exact metadata below; do not overwrite existing labels just to change color or description.

- `prd`
  - Color: `5319e7`
  - Description: "generated by `/to-prd`, marks product requirements documents that define scope, user stories, implementation decisions, and testing expectations"
- `issue`
  - Color: `7f1e50`
  - Description: "generated by `/to-issues`, marks implementation-ready vertical slices derived from a PRD or plan"

5. Write the PRD using the template below, then publish it to the project issue tracker. Apply the `prd` label and the `ready-for-agent` triage label - no need for additional triage.

<prd-template>

## Problem Statement

The problem that the user is facing, from the user's perspective.

## Solution

The solution to the problem, from the user's perspective.

## User Stories

A LONG, numbered list of user stories. Each user story should be in the format of:

1. **US-1** — As an <actor>, I want a <feature>, so that <benefit>

<user-story-example>
1. **US-1** — As a mobile bank customer, I want to see balance on my accounts, so that I can make better informed decisions about my spending
</user-story-example>

This list of user stories should be extremely extensive and cover all aspects of the feature.

## Acceptance and Test Mapping

Map every user story to one or more externally observable acceptance criteria.
For every criterion include:

- **User story:** its `US-N` identifier
- **Acceptance criterion:** the observable outcome that must hold
- **Test seam:** the highest practical public interface through which it is verified
- **Verification:** automated or human, with the reason for that choice

Every user story must appear in this mapping. A criterion may cover multiple
stories when the relationship is explicit.

## Implementation Decisions

A list of implementation decisions that were made. This can include:

- The modules that will be built/modified
- The interfaces of those modules that will be modified
- Technical clarifications from the developer
- Architectural decisions
- Schema changes
- API contracts
- Specific interactions

Do NOT include specific file paths or code snippets. They may end up being outdated very quickly.

Exception: if a prototype produced a snippet that encodes a decision more precisely than prose can (state machine, reducer, schema, type shape), inline it within the relevant decision and note briefly that it came from a prototype. Trim to the decision-rich parts — not a working demo, just the important bits.

## Testing Decisions

A list of testing decisions that were made. Include:

- A description of what makes a good test (only test external behavior, not implementation details)
- Which public seams will be tested and which modules they exercise indirectly
- Why each selected seam is the highest practical place to prove the behaviour
- Prior art for the tests (i.e. similar types of tests in the codebase)

## Out of Scope

A description of the things that are out of scope for this PRD.

## Further Notes

Any further notes about the feature.

</prd-template>
